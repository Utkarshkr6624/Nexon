# Migrations (Alembic)

Schema history for the NEXUS backend. Every schema change is a versioned,
reviewable script — the database is never mutated by `create_all()`.

## Layout

```
backend/
├── alembic.ini                 # Alembic config; holds NO credentials
└── migrations/
    ├── env.py                  # offline + online (async psycopg3) runner
    ├── script.py.mako          # template for `alembic revision`
    ├── README.md               # this file
    └── versions/
        └── 0001_initial_create_users.py
```

## Prerequisites

- Run everything from `backend/` (or pass `-c backend/alembic.ini`).
- A `.env` (copy `.env.example` to the repo root) or equivalent environment
  variables must be present, because `migrations/env.py` builds the connection
  URL from `app.core.config.get_settings().sqlalchemy_database_uri`.
- `alembic upgrade head` requires the target database to exist. This project
  does not create databases for you; only tables within them.

## Commands

| Command | What it does |
| --- | --- |
| `alembic current` | Show which revisions are applied to the database. |
| `alembic heads` | Show revision heads known to the code. |
| `alembic history --verbose` | Show the full revision graph. |
| `alembic upgrade head` | Apply every pending migration. |
| `alembic upgrade +1` / `+1` (downgrade) | Move one step forward / back. |
| `alembic downgrade -1` | Roll back the most recent migration. |
| `alembic downgrade base` | Roll back to an empty database. |
| `alembic revision -m "add widgets"` | Create a new, empty revision file. |
| `alembic revision --autogenerate -m "..."` | Create a revision from model drift. |
| `alembic upgrade head --sql` | Offline mode: print the SQL, touch nothing. |
| `alembic check` | Exit non-zero if models and database disagree. |

All of the above are run from `/e/Nexo/backend`:

```bash
cd /e/Nexo/backend
alembic upgrade head
```

## The database URL

`alembic.ini` deliberately ships with an empty `sqlalchemy.url`. Credentials in
a git-tracked file are a bug waiting to happen; `env.py` supplies the real
async URL from the settings singleton instead:

```
postgresql+psycopg://<user>:<password>@<host>:<port>/<database>
```

To migrate a different database without editing any file, override the
environment for that one command:

```bash
# the pytest database
DATABASE_URL=postgresql+psycopg://nexus:nexus@localhost:5432/nexus_test \
  alembic upgrade head
```

Because `sqlalchemy.url` is empty by default, `get_url()` falls back to the
settings singleton — but if you *do* set a non-empty `sqlalchemy.url` in a
local, untracked copy of the config, that value wins.

## Async driver

The project uses SQLAlchemy 2.0 in async mode with **psycopg3**
(`postgresql+psycopg`). Alembic cannot run migrations on an async engine
directly, so `env.py`:

1. builds the engine with `create_async_engine(...)` and a `NullPool` (migrations
   are short-lived processes; a pool buys nothing),
2. opens one connection,
3. calls `await connection.run_sync(do_run_migrations)` so each migration step
   executes on the synchronous side of the greenlet bridge.

Do not "simplify" this into `engine.connect()`.

## Windows notes

Two things bite on a stock Windows + psycopg3 setup:

1. **Event loop.** psycopg's async mode refuses the default ProactorEventLoop.
   `env.py` passes `loop_factory=asyncio.SelectorEventLoop` on `win32` so
   `alembic` works out of the box. Any long-lived async process (the FastAPI
   app) needs the same treatment — see `app/main.py`.
2. **Use `127.0.0.1`, not `localhost`.** When `localhost` resolves to `::1`
   first, psycopg's *async* connect path hangs on a filtered IPv6 socket while
   the plain sync path falls back to IPv4 without complaint. If `alembic`
   appears to freeze, set `POSTGRES_HOST=127.0.0.1` or point `DATABASE_URL`
   at `127.0.0.1` in `.env`.

## Autogenerate workflow

1. Edit the model under `backend/app/models/`.
2. Create the revision:
   ```bash
   alembic revision --autogenerate -m "describe the change"
   ```
3. **Read the generated file.** Alembic compares model metadata against the live
   database and is wrong often enough that an unreviewed autogenerated revision
   is worse than a hand-written one. In particular, it cannot see renames (it
   emits drop + add, which loses data) and it cannot infer data backfills.
4. Run `alembic check` to confirm no drift remains.

The revision file is the source of truth for a database, so it must never import
`app.models` — otherwise changing a model would silently change the meaning of
past migrations. `0001_initial_create_users.py` writes its DDL out explicitly for
this reason. When you change a model, add a *new* revision; never edit an applied
one.

## Conventions

- One revision per logical change; the message becomes the file name.
- `downgrade()` must work. A migration you cannot roll back is a migration you
  cannot deploy safely.
- `env.py` autogenerates with `compare_type=True` and `compare_server_default=True`,
  so type and server-default drift is caught rather than ignored.
- Autogenerate is limited to the `public` schema and skips `alembic_version` and
  `spatial_ref_sys`.
